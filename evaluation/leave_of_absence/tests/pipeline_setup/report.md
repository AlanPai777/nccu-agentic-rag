# 流程測試（pipeline_setup）：如何辦理休學（程序類、跨處室，60 個 keypoint），用假設的答案讓整條評測管線跑一次

**日期**：2026-11-13
**這不是系統的真實答案，下面的分數不能當評測結果。** 目的：檢查整條管線在一題「長答案、很多 keypoint、很多條件式」的題目上走不走得通。
答案是 Claude Code 寫的（`answers/`）。證據：教務處頁面、學務處退費標準頁、三張表單用 `output/` 的真實快照；**辦公室聯絡資訊那一則是假設的**（用 `evaluation/registry/registry.json` 照 `contact_node` 的版面排出來，名字取快照寫法，現場才有的人用現場寫法），不是真實 run 的輸出。`model`／`system_version`／`label` 都標「假設」。不放 `runs/`。`make_runs.py` 沒有單元測試。

## 發現

1. **長答案沒有問題**：`complete` 切成 43 個主張，全部有依據，引文全部驗證通過；子代理回報比較沒把握的只有表格換行造成的怪空格與一個標題當主張。
2. **選擇性的 keypoint 仍然計入 Completeness 的分母**：`complete` 是一份完整的好答案，只因為沒寫選擇性的 K8（轉系取消資格）、K45（平安保險費繳費）、K46～K48（新生與轉學生註冊三項），Completeness 是 0.92，不是 1.00。`required` 欄位目前只是備註，評分不看它（設計文件 F8、F9 一類，跨題的規則，凍結前要決定，這裡沒有改）。這題的 60 個 keypoint 裡有 14 個選擇性、9 個條件式，所以「好答案的上限」明顯低於 1，彙整時要小心不能直接當分數比。
3. **「答對但沒依據」又出現（`live_names` 的 K53、K55）**：答案寫「陳源宗（分機 67161）」「盧小姐（分機 62226）」，登記表與規則版都認為對（陳源宗是現場頁住宿組 67161 的人，快照是張君豪；盧小姐是姓氏加稱謂），但假設證據的名字是快照寫法，所以回推判 unsupported。這跟第 4 題同類，是預期行為：系統讀到哪個來源，主張才有依據。這題多了一個真實的例子：**同一個分機的人換過**（住宿組 67161），答案寫舊名或新名都算對，但要看證據裡有沒有。
4. **寫錯的事實都抓得到（`wrong_facts`）**：時限、休學年限、修課紀錄、住宿組適用對象、退費 1/2 與逾 1/3 不退、平安保險費、承辦單位共 11 個 keypoint 判 wrong，規則版與判斷一致；原資中心、國合處、委託書沒提到，不計入。
5. **條件式的 keypoint 在答案提到單位但沒寫細節時判 irrelevant（`live_names` 的 K26、K27、K40）**：這是 `applies_if` 的設計，沒有問題；但它讓精簡的答案 Completeness 偏低（0.63），與第 2 點同理。
6. **沒有發現新的程式問題**：這次的程式計分、回推、判斷、算分都沒有出錯，第 4 題修好的規則（樓層範圍、盧小姐）在這題直接適用。
7. **假設證據的限制**：辦公室聯絡資訊是用登記表排的，真實的 `contact_node` 讀的是舊索引；出納組、住宿組等的現場新舊差異（議題 F19）要等真實 run 才看得到影響。
