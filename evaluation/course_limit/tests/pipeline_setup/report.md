# 流程測試（pipeline_setup）：選課上限題，用假設的答案讓整條評測管線跑一次

**日期**：2026-11-11
**這不是系統的真實答案，下面的分數不能當評測結果。** 目的只有兩個：檢查整條管線在第一題非聯絡人題上走不走得通，以及找出判斷規則的灰區。
答案是 Claude Code 寫的（`answers/`），證據用 `sources/snapshot/` 裡真實的頁面原文（學則、FAQ、選課須知）包成 `get_page` 工具輸出的樣子，`model`／`system_version`／`label` 都標「假設」。
不放 `runs/`，所以 `list_runs.py` 與之後的彙整都讀不到。`make_runs.py` 沒有單元測試。

## 做了什麼

| 案例 | 答案 | 想看什麼 |
|---|---|---|
| `complete` | 把標準答案換個說法寫出來（5 個 keypoint 全涵蓋） | 流程走得通；全部 relevant |
| `partial` | 只說「上限 25、雙主修 31」 | 漏了輔系 28、超減修、碩博士、下限，怎麼判 |
| `wrong` | 上限寫 24（標準 25）、輔系寫 30（標準 28），其餘照寫 | wrong 怎麼判、怎麼算分 |

流程：`make_runs.py` 組 `prediction.json` → 階段 2（`score_programmatic.py`）→ 階段 3 `prepare` → **隔離回推**（三個全新的 general-purpose 子代理，一份答案一個，只給 `trace_input.json`；提示詞與 `tampered_v2` 用的逐字相同，只有路徑不同）→ `audit_subagent_tools.py` → `check` → `verify_run.py` → Keypoint 判斷（Claude Code）→ `score`。
沒有呼叫 ollama，沒有對 nccu.edu.tw 發任何請求。

## 找到的灰區（只記錄，沒有決定規則）

### 1. K2、K5 各含兩個事實，違反「一個 keypoint 一個事實」（影響最大）

K2 是「雙主修 31、輔系 28」，K5 是「下限 12、10」。`gold-rules.md` 本來就寫「一句原文含多件事要拆成多個 keypoint」，這一題的 gold 違反了它，`kind=semantic` 只是繞過去。造成三個後果：

- **只講一半該怎麼判**：`partial` 只說雙主修 31、沒說輔系 28。判斷規則寫「最重要的資訊一致即可」，我判 relevant，結果 K2 拿滿分，`partial` 的 Completeness 變成 0.40（K1、K2 兩個），其實 K2 只對一半，**過度給分**。判 irrelevant 也講得通；規則沒說，所以是灰區。
- **一半對一半錯**：`wrong` 的 K2 雙主修 31 對、輔系 30 錯，判 wrong。連帶 c4（「雙主修 31」，事實是對的）因為連到 wrong 的 K2，被算成不正確，以主張為單位的精確率被拉低（9 個主張只算 6 個正確）。
- 拆成單一事實後，每個 keypoint 都能設成 `hard`，不需要 `semantic`，也不需要規則版支援「全部都要出現」。

**建議（需要你決定，gold 沒有改）**：K2 拆成「雙主修 31」「輔系 28」，K5 拆成「下限 12」「下限 10」，共 7 個 keypoint。

### 2. 規則版的 `hard` keypoint 被換個說法誤判

`complete` 與 `wrong` 的答案寫「由各系（所）**自行訂定**」，gold 的 K4 可接受寫法有「自定」「各系所自定」等，沒有「自行訂定」，規則版判 miss，Claude 判 relevant。這正是設計文件第 1 節說的「keyword 太窄冤枉正確答案」，`disagreements` 機制照設計把它列了出來。**不要調整其中一方讓它們一致**（判斷規則的原則）；要不要把「自行訂定」「自行決定」加進可接受寫法，需要你決定。

另外，`wrong` 的 K1（24 對 25）規則版只能判 miss，不能判 wrong（沒有 `value_check`）；Claude 判 wrong。兩者都不算命中，所以沒有列為不一致。

### 3. 「推論」與「否定」的主張算不算有依據

主張 c9「沒有全校統一的上限」：證據只寫「碩、博士班學生每學期修習學分由各系(所)自定」，沒有一句說「沒有全校統一的上限」。`complete` 與 `wrong` 兩個子代理都判 supported，也都自述「不確定，是推論」。回推規則第 4、5 條（supported 要有證據、只看證據文字）沒有說推論或否定句怎麼處理。若從嚴，c9 是 unsupported，`complete` 的有依據比例會是 8÷9，不是 9÷9。**需要規則決定**；這是兩個獨立子代理做了同樣的選擇，不是偶然。

### 4. 非聯絡人答案的切法（初步觀察）

- 切得比我預期的細：`complete` 的 4 段文字切成 9 個主張，每個事實一個，在逗號處分開；沒有重疊；規則 7（人員行）沒有用到。
- 條件與結果被分成兩個主張：「經系主任核可，可在當學期申請超修或減修學分」（c6）與「超減修最多以 6 學分為限」（c7），兩者都連到 K3。
- 片段會失去主語：c2「第一至第三學年每學期不得少於 12 學分」沒有「學士班學生」。
- 答案是我寫的、比真實答案整齊，這些只是**趨勢**，真實的 Gemma 答案（雜亂、重複、帶來源行）要等有 run 才知道。

## 限制

- 答案、Keypoint 判斷都是 Claude Code 做的，我知道哪裡是故意寫錯的，判斷**不獨立**；這個測試只驗證機制，不驗證判斷品質。
- 證據是我挑的三頁，不是系統自己檢索的；檢索漏斗（頁面→清單→答案）沒有測。Context 句子的精確率 0.010、詞 0.028 只是因為整頁（學則 13,216 字）都算進去，沒有意義（設計上本來就只供比較）。
- 每個案例一個子代理、一次執行；LLM 每次輸出不同。
- 子代理只查了工具呼叫，看不到推理；只查這一次。

## 後續（都需要使用者決定）

- 灰區 1：K2、K5 要不要拆成單一事實（建議拆；拆了之後灰區 1 的三個後果都消失）。
- 灰區 2：K4 的可接受寫法要不要加「自行訂定」等。
- 灰區 3：推論或否定句的主張要不要在回推規則裡寫明（支持／不支持）。
- 等有真實 run 之後，再看非聯絡人答案的切法，決定要不要為這一類題型寫切法指引。
