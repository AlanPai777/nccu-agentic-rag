# docs/upper_bound/ — 跨處室 Eval 驗證總表

## 總結（2026-09-18，本輪收尾）

`rag/eval.py` 原有 6 組 criteria 都聚焦在單一處室或單一鏈路。這一輪新增 5 題，各自代表一種語料庫裡實際存在的「跨處室」架構模式，逐題查原文、設計 criteria、跑 `agentic_rag.py` 拿真實輸出、人工核對答案品質。掃過剩下的候選表單（新生學分抵免、通識學分認定、兵役狀況調查）後，確認都不是新架構——分別是 Question004 的重複模式、Question003 的簡化子集、或根本不算跨處室——決定在 5 題收尾，不再硬湊題數。

**5 個架構模式 × 分數**

| 模式 | Question | 最終分數 |
|---|---|---|
| 並行雙處室 | 001 轉系所 | 12/12 |
| 鏈式依賴 | 002 退宿保證金 | 12/12 |
| 三段連續審核 | 003 雙主修輔系 | 10/12 |
| 條件分岔 | 004 交換學分抵免 | 12/14 |
| 跨機構 | 005 台聯大跨校雙主修 | 3/14 → 9/14（修正後） |

**這一輪的產出，分三類：**

1. **新增的 eval 基礎設施**：`rag/eval.py` 拆成 `rag/eval_criteria/` package（一個 query 家族一個檔案），5 組新 criteria 全部註冊進 `QUERY_CRITERIA_MAP`，`python agentic_rag.py "query"` 可直接對這 5 題自動評分。
2. **修好的 criteria bug（3 個，純粹是評分機制的問題，answer 本身沒事）**：Question002/003 各一個「keyword 太窄冤枉正確答案」（用詞跟語料庫原文不同、數字格式中英文差異）；Question004 一個相反方向「keyword 太鬆讓真缺漏矇混過關」（`credit_limit` 跟 `application_deadline` 共用「三分之一」子字串撞字）。
3. **修好的一個真實系統缺陷**：Question005 發現 `_judge_candidates`（`rag/agentic/logic/rewrite.py`）把候選頁面裡一個連結的錨點文字誤判成頁面本身內容，導致答錯完全不相干的合作對象（北藝大 vs 台聯大）。修正方式是資料層的通用 `_strip_md_links()`，不是針對這一題寫的 prompt 規則（第一次嘗試的 prompt 規則被要求撤回）。已用 Question005 本身（3/14→9/14）+ 休學回歸測試（25/26，跟既有基準一致）驗證無迴歸。

**還沒解決、留給下一輪的發現**（不影響本輪 criteria 判定，記在下方「獨立發現」）：模糊查詢時 agent 找到第一個候選就停、不會確認涵蓋度（Question002）；synthesis 有時會漏掉表單裡的「注意事項」類次要規則，即使內容已經在 context 裡（Question003）；CLI 預設 trace 看不到 `resource_node`/`contact_node` 抓到的內容，容易讓人誤判「檢索沒抓到」跟「抓到了但沒寫進答案」。

---

這批驗證專門測「跨處室」——一題需要橫跨兩個以上處室/審核層才能答對，用來檢驗 `resource_node`/`contact_node`/`agent_node` 多輪工具呼叫在有跨處室依賴時的穩定度。

每題流程：讀 `output/` 原文查證（Sonnet 直接讀，非查記憶）→ 設計 query + criteria → 跑 `agentic_rag.py "query"` 拿真實輸出 → 人工判斷答案品質 → 對照分數決定 criteria 要不要改 → 記錄結論。

**扣分不等於答案錯**——每題都要先判斷落在哪一類，才能決定要不要修 criteria：
1. 答案真的錯/幻覺 → 系統缺陷，如實記錄，不改 criteria。
2. 答案正確完整，只是用詞跟 criteria 預期的字面不同 → criteria 設計問題，修 criteria。
3. 答案對某一種合理解讀完整正確，但 query 本身模糊、criteria 只認一種解讀 → 檢討 query 設計。
4. 答案對它實際檢索到的範圍正確，但檢索/涵蓋度本身不完整 → 真實系統缺陷，但缺陷點在「沒探完」不是「編造」，criteria 維持原樣如實記錄。
5. 內容其實已經被檢索到（在 context 裡），但 synthesis 沒寫進最終答案 → 真實系統缺陷，但缺陷點在 synthesis 遺漏，不是檢索沒探完——修法不同（改 synthesis prompt vs. 改檢索邏輯），要分開記錄。**注意**：目前 CLI 預設 trace（`_render_messages()` 跳過 `HumanMessage`）看不到 `resource_node`/`contact_node` 抓到的內容，很容易把第 5 類誤判成第 4 類，判定前務必留意這個觀測盲區（見下方獨立發現）。
6. Criteria 關鍵字跟同一份來源文件裡「另一件事」共用字串，造成假陽性（答案其實缺漏，卻被誤判命中） → criteria 設計問題（方向跟第 2 類相反：第 2 類是太窄害正確答案被扣分，第 6 類是太鬆讓真正缺漏矇混過關），改用更完整的片語避免撞字。
7. 答案對「它檢索到的」內容正確、無幻覺，但檢索到的根本是同名不同實體的另一個對象（主題詞重疊但機構/對象不同）→ 真實系統缺陷，是 `search_texts` 的 judge 辨識力不足，不是 criteria 問題，維持原樣如實記錄。跟第 4 類（沒探完）不同：第 4 類是「該讀的都讀了只是漏一部分」，第 7 類是「一開始就選錯候選」，嚴重度更高。

判斷方法固定用**人工讀完整答案內容**去核對每一項 criteria 到底有沒有真的命中，不要用「猜測系統內部哪個節點有沒有跑」來判斷（trace 本身有第 5 類提到的觀測盲區，容易誤判）。

## 已修正的系統缺陷

- **`_judge_candidates` 把連結錨點文字誤判為頁面內容**（Question005 發現，2026-09-18 修正）：`rag/agentic/logic/rewrite.py` 新增 `_strip_md_links()`，在組出候選頁面摘要給 judge 看之前，先把候選頁面裡完整的 markdown 連結（錨點文字+網址）整段拿掉——根因是候選頁面若開頭放一個「指向別處」的連結，且連結的錨點文字剛好跟查詢用詞重疊，judge 只做表面文字比對就會誤判匹配，即使頁面本身講的是完全不同的事。這是資料層的通用修正，不是針對「台聯大」寫的特殊 prompt 規則（曾嘗試用 prompt 規則修但被要求撤回，改走這個方向）。已用 Question005（3/14 → 9/14）跟休學回歸測試（`如何辦理休學`，25/26，跟既有基準一致）驗證：修掉了本題的問題，也沒有把其他已知能答對的查詢改壞。

## 獨立發現（不對應特定 criteria，僅記錄）

- **「如何辦理退宿」（模糊查詢）**：agent 找到第一個候選（學期前退宿 `QP-M03-01-04`）就收斂作答，從未探索「離宿保證金」（`QP-M03-01-05`）這一半同樣合法的情境，`self_eval_node` 未攔下。答案本身無幻覺，但對模糊查詢的完整涵蓋度不足。詳見 `Question002_dorm_checkout.md`「模糊查詢的獨立發現」一節。歸類：KNOWLEDGE 路徑「找到第一個候選就停」的既有已知模式（CLAUDE.md Known issues）在跨處室情境下的新實例。
- **Question003（雙主修輔系）— synthesis 遺漏「注意事項」類規則**：表單全文（含「視同自願放棄」那條規則）很可能已經被 `resource_node` 抓進 context，但 synthesis 沒有把它寫進最終答案。跟 Question002 的「檢索沒探完」不是同一種失敗，這裡檢索大概率是完整的，是生成階段對「規則/注意事項」類次要資訊的涵蓋不穩定。詳見 `Question003_double_major_minor.md`。
- **CLI trace 對 `resource_node`/`contact_node` 內容不可見**：`_render_messages()`（`rag/agentic/logic/rewrite.py:79-91`，CLI 預設輸出跟 `rewrite_node` 內部共用）只印 `AIMessage`/`ToolMessage`，完全跳過 `HumanMessage`——而 `resource_node`/`contact_node` 抓到的表單全文/聯絡資訊都是用 `HumanMessage` 塞進對話。這代表光看預設 trace，沒辦法分辨一個缺漏的事實是「檢索沒抓到」（上面第 4 類）還是「抓到了但 synthesis 沒寫」（第 5 類）——這兩者修法不同，卻長得一模一樣，Question003 一開始就因此誤判。值得之後讓 trace（至少 `--stream` 模式）也印出 `HumanMessage` 內容，哪怕只印開頭標記行。
